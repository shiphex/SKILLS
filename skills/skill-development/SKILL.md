# 技能开发指南

使用本技能创建或更新 Claude Code 技能。目标是把真实专业知识、稳定流程和可复用工具封装成轻量、准确、可评估的技能，而不是生成泛泛的“最佳实践”文档。

## 工作原则

- 从真实任务、项目资料、运行记录、代码审查、事故复盘、API 规格、样式规范或用户纠正中提炼技能。不要只依赖模型常识。
- 只写 Claude 不容易自然知道、但会影响成败的信息：项目约定、领域流程、工具选择、易错点、输入输出格式、验证方式。
- 保持技能边界清晰。一个技能覆盖一个连贯工作单元；过窄会导致多个技能同时加载，过宽会降低触发精度。
- 优先给默认方案，而不是列一组等价菜单。只有在替代方案真正影响结果时才说明何时切换。
- 让指令复用到一类任务。避免写成只适用于当前请求的一次性答案。
- 按任务脆弱程度控制自由度：灵活文本任务给原则和判断标准；脆弱、重复、易错任务给明确步骤或脚本。
- 保持 `SKILL.md` 精简。接近 500 行或包含大量条件细节时，使用渐进披露，把细节拆到 `references/`、`scripts/` 或 `assets/`，并在正文中说明何时读取或运行。

## 创建流程

1. 明确用户意图和成功标准：
   - 识别技能要帮助 Claude 完成什么任务、面向谁、输出什么结果。
   - 收集 3 到 5 个真实或逼真的用户请求样例。
   - 标出哪些请求应该触发技能，哪些相邻请求不应该触发。
   - 确认技能是新建还是更新，放在个人级 `~/.claude/skills/`、项目级 `.claude/skills/`，还是额外目录。

2. 提炼可复用专业知识：
   - 从样例中找出 Claude 可能会猜错、漏掉或反复重写的部分。
   - 记录固定流程、项目约定、工具/API 用法、文件格式、错误恢复方式和验证标准。
   - 把用户纠正过的做法写成具体 gotcha，例如“必须使用 X，不要使用 Y”，而不是“遵循最佳实践”。

3. 设计技能边界和目录：
   - 技能目录名使用小写字母、数字和连字符，最长 64 字符；`name` 与目录名保持一致。
   - 必需文件是 `SKILL.md`。默认只创建它，除非有明确复用价值再添加资源目录。
   - 用 `scripts/` 存放确定性、重复、脆弱的可执行逻辑。
   - 用 `references/` 存放按需读取的长文档、规范、schema、API 说明或领域资料。
   - 用 `assets/` 存放输出会使用但不需要读入上下文的模板、图片、字体、样例工程或其他素材。
   - 不创建无关的 `README.md`、安装指南、更新日志或过程说明。

4. 编写 frontmatter：
   - 默认只写 `name` 和 `description`。
   - `description` 决定 Claude 是否自动加载技能；把关键触发语义放在这里，而不是放在正文的“何时使用”章节。
   - 用用户意图描述触发条件，不用内部实现描述。例如写“当用户要批量整理 Excel 财务报表时使用”，不要只写“提供 pandas 脚本”。
   - 适度主动：列出用户可能不会明说但仍应触发的场景。
   - 保持简洁，避免泛化到相邻任务。
   - 仅在确有需要时添加 Claude Code 字段：
     - `argument-hint` 或 `arguments`：技能需要手动调用并接收参数时使用。
     - `allowed-tools`：技能运行时应授予特定工具权限时使用。
     - `context: fork` 和 `agent`：技能内容本身是一项可交给子代理独立执行的任务时使用。
     - `paths`：技能只应在特定文件模式下自动激活时使用。
     - `disable-model-invocation: true`：只允许手动调用时使用。

5. 编写 `SKILL.md` 正文：
   - 使用命令式、步骤化语言，直接告诉 Claude 怎么做。
   - 开头说明目标和核心约束，不重复解释 Claude 已经知道的通用概念。
   - 放入最常用流程、默认工具、关键 gotchas、输出模板和验证循环。
   - 对多步骤工作使用清单，让 Claude 能跟踪进度。
   - 对需要固定格式的输出提供短模板；长模板放入 `assets/` 并说明何时使用。
   - 对按需资料使用明确引用，例如“当 API 返回非 200 时，读取 `references/api-errors.md`”，不要只写“查看 references”。

## 脚本与资源

只有在脚本能减少重复、提高确定性或避免脆弱手工步骤时才添加 `scripts/`。

设计脚本时遵守：

- 使用相对路径在 `SKILL.md` 中引用脚本，例如 `scripts/validate.py`。
- 通过命令行参数、环境变量或 stdin 接收输入；禁止交互式提示、确认菜单或密码对话框。
- 提供简洁的 `--help`，说明用途、参数、默认值和示例。
- 输出优先使用 JSON、CSV、TSV 等结构化格式；进度和诊断写到 stderr。
- 错误信息说明问题、期望输入和下一步尝试，避免只输出“invalid input”。
- 固定依赖版本。Python 脚本优先使用 PEP 723 内联依赖并通过 `uv run scripts/name.py` 运行；其他运行时也应把依赖声明放在脚本或命令中。
- 添加脚本后实际运行代表性样例，确认输出和错误路径可被 Claude 理解。

添加 `references/` 时遵守：

- 只放正文不适合常驻上下文、但执行时可能需要的材料。
- 每个引用文件都必须从 `SKILL.md` 直接说明读取条件。
- 超过约 100 行的引用文件在顶部加入目录。
- 不在 `SKILL.md` 和引用文件中重复维护同一段信息。

添加 `assets/` 时遵守：

- 只放输出会复制、修改或引用的素材。
- 不要求 Claude 先把资产全文读入上下文。
- 在 `SKILL.md` 中说明何时使用哪个资产。

## 描述优化

用真实查询评估 `description` 是否能正确触发。

1. 建立查询集：
   - `should_trigger: true`：用户想创建或更新该技能覆盖的任务。
   - `should_trigger: false`：相邻但不需要该技能的任务。
   - 查询要像真实用户说话，包含省略、别名、路径、目标和模糊表达。

2. 多次运行触发测试：
   - 同一查询运行 3 次作为起点，因为触发可能有随机性。
   - 记录触发率。正例触发率应高于阈值，负例触发率应低于阈值；默认阈值可用 0.5。

3. 防止过拟合：
   - 将查询分成训练集和验证集，例如 60% / 40%。
   - 只用训练集失败样例修改描述。
   - 修改后同时检查训练集和验证集，确认泛化没有变差。

4. 修改规则：
   - 正例没触发时，在 `description` 加入缺失的用户意图或触发语境。
   - 负例误触发时，收紧范围，去掉过宽词语或增加边界。
   - 不把验证集具体措辞硬塞进描述。

## 输出质量评估

为技能建立小而真实的 eval，检查技能是否真的提升结果，而不只是能被触发。

- 每个 eval 包含用户提示、必要输入文件、期望产物和可验证断言。
- 断言要具体、可观察、可计数或可由脚本检查，例如“输出文件是合法 JSON”“报告至少包含 3 条建议”“图表有坐标轴标签”。
- 避免“结果很好”这类不可判定断言，也避免要求完全固定措辞。
- 对机械条件使用脚本评分；对风格、设计、判断质量使用人工或模型评审，并要求给出证据。
- 查看完整执行轨迹，而不只看最终答案。若 Claude 浪费时间、读取无关资料、反复尝试工具或跳过验证，把对应修正写回技能。
- 记录成功和失败样例。成功样例能暴露哪些说明可以删减，失败样例能暴露缺失的 gotcha 或流程约束。

## 迭代和更新现有技能

更新技能时先读取现有 `SKILL.md` 和已引用资源，再改动。

- 保留仍有效的触发语义、流程和资源引用。
- 删除过时、重复、泛泛或不会改变行为的说明。
- 把新发现的用户纠正、失败模式和验证步骤写入最靠近使用点的位置。
- 若新增资源，确保 `SKILL.md` 明确说明何时使用它。
- 修改 `description` 后重新检查正例和负例，避免触发范围漂移。
- 修改脚本后至少运行代表性成功路径和一个错误路径。

## 完成前检查

- `SKILL.md` 存在，frontmatter YAML 可解析。
- `name` 与目录名一致，并符合小写字母、数字和连字符规则。
- `description` 写清“做什么”和“何时使用”，且不过宽。
- 正文只包含执行任务需要的高价值信息。
- 资源目录只在有明确用途时存在，并从 `SKILL.md` 直接引用。
- 脚本非交互、可查看帮助、错误可行动、输出可解析。
- 至少有 3 个应触发样例和 2 个不应触发样例用于人工或脚本评估。
- 最终回复说明创建或更新了哪些文件，以及已完成哪些验证。
